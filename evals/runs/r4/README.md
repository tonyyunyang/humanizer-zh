# 第四轮：Issue 与 PR 的协作表达

这轮检查 issue 和 PR 描述能否更好地支持定位、讨论和审阅，同时保留此前按具体表达目的改稿的方向。研究依据见 [ISSUES-AND-PRS.md](../../../docs/ISSUES-AND-PRS.md)。不以更短、更多标题或更像固定模板作为统一标准。

保留 `7d5bfed` 的 22 行条件性指导，正文为 178 行。16 份实际改稿通过本轮评审的信息与范围门槛；初次偏好在两版之间各有两项，四项平局。对四项非平局结果互换顺序后，全部判为平局，因此没有建立新版文风更好的稳定证据。完整计数和逐例理由见 [summary.json](summary.json)。

## 固定设置

- 起点：`06bcffe`，运行正文与第三轮保留的 `e4946cf` 相同。
- 候选：`7d5bfed`，正文 178 行，新增 22 行条件性协作编辑指导与例子；其余语言、信息与表达目的规则不变。
- 独立案例：`a76f659` 固定的 [r4-cases.json](../../rounds/r4-cases.json)，八份不同原文，四项开发、四项保留。
- 出题会话不读仓库、skill、既有案例、调研或候选改动；维护代理先读开发组，候选固定后才打开保留组内容。
- 编辑与评审使用 `gpt-6-astra`、`max`，独立临时会话。编辑超时 240 秒，评审超时 300 秒；生成设置保持可比较。
- 沿用第三轮已校准的评审提示与 schema，不新增鼓励短文或模板填充的评分项。评审可见案例的具体验收要点，改写会话不可见。
- 本次交互式迭代预设上限 36 次，实际完成 16 次编辑、8 次匿名比较和 4 次顺序复核，共 28 次有效执行，没有失败或重试。定期任务原有的每次 16 次上限不变。

## 候选判断

原有 skill 已能处理套话和信息保护。本轮补充协作任务需要的内容选择：让问题可处理，让改动可审阅；标题和开头说明具体事项，保留诊断证据、最终方案的理由与实际验证，尊重项目模板和明确的修改范围。复杂取舍可以写长，未提供的信息不能补成肯定或否定的事实。

范围属于编辑说明文字，不扩展为执行样例命令、编写修复、提交表单或发布内容。保留组也用于检查这些要求是否侵入其他写作任务。保留候选的理由是落实新的应用要求，当前没有发现需要撤回的信息回退；专业资料与少量输出都不能证明整体效果更好。

## 评审与覆盖的限制

第三轮的小型校准支持继续使用同一评审提示，但本轮四项非平局偏好都未能在顺序复核中重现。不能仅凭这次检查区分位置影响与模型的普通波动，也不能将复核结果覆盖原判断后宣布“八项都一样好”。保留两次判断，更稳妥的结论是本轮没有稳定的文风优势。

八份独立合成原文包含七项 issue/PR 任务和一项其他表达，只有四项保留案例，每版每项只生成一次。模型生成与评审可能共享偏好，没有测量真实维护者的阅读时间、评审质量或合并结果。这里的通过仅指已检查的案例，不是失败率估计、作者身份判断或所有场景下的质量保证。

本轮保留了模板内已有的验证事实，但没有单独测试固定模板要求填写验证、材料却完全没有验证记录的情况。也没有覆盖真实仓库调查、根据最终 diff 起草、所有永久回归或其他模型。这些不能从当前通过项推定。

仓库结构校验、skill-creator 校验和 diff 检查通过；14 项研究脚注都有定义且被引用。本轮没有修改包装或维护代码，没有重跑其单元测试，也不把静态检查计成行为收益。

## 下一阶段

第三、四轮都未建立稳定的整体文风优势。本阶段保留明确的表达目标和这次要求的协作覆盖，停止围绕这些已经看过的材料继续增加近似规则。

后续优先使用获得许可的真实作者改稿、维护者反馈，以及缺失验证资料、开发过程记录和最终 diff 等新的独立材料。先找可说明的问题，再决定是否需要修改。八个案例以后作为开发材料使用，不能再宣称是未见测试。
