# 中文编辑的改进循环

这个循环维护的是根目录的写作 skill。目标是根据具体表达需要，润色自然中文及中英混排，持续减少模板化的措辞、结构、节奏和姿态，同时保住原意。判断来自用户要求、上下文与句段作用，不按文体名称设固定风格，也不把平直视为缺陷。案例、脚本和研究只供维护使用，不要求日常改稿加载。

专业依据与采用边界见[编辑依据](GROUNDING.md)。每轮把来源中的观察变成一个可检验的编辑假设，再通过实际输出决定取舍；不把引用专业资料本身当作效果证明。

Issue 与 PR 的内容选择依据见[协作写作调研](ISSUES-AND-PRS.md)：先帮助读者定位、讨论或审阅，所需信息和篇幅随具体任务变化。它与中文表达规则共同适用，不引入固定语气或一律压短的要求。

## 一轮怎样进行

1. **固定起点。** 把当前可用版本提交到 Git，记录模型、推理设置和案例版本。正文的改进、评测方法的修正和验证结果都可以分别 commit，不把未验证的候选写成已证明的提升。
2. **运行前测。** 每个案例开启新的模型会话。改写模型只接收 skill、用户要求、样文和原文，不接收预期答案、失败假设或版本名称。原始输出原样留存，失败、超时和工具调用异常也记录。
3. **找具体问题。** 先审阅事实、归属、否定、条件、范围、时间、作者立场和精确字符，再看重点、承接、句式与节奏是否合乎这次表达。选有代表性、可复现的问题，不根据一次偶然措辞加通用禁令。
4. **做一个小候选。** 改最相关的一处，优先改清原有指令或例子。每条新规则要有收益例子和保留反例。候选先 commit 为实验版本，随后由验证决定保留、修订或撤回。
5. **成对比较。** 用同一模型、设置和输入运行起点与候选。评审时随机交换两个输出的顺序，隐藏版本身份。评审者不接收候选的改动说明；记录平局、取舍和不确定结论。
6. **检查新案例。** 候选固定后才打开保留集。它由独立会话按具体表达需要编写，出题者不读 skill、已有案例或当前失败假设。看过的保留集在下一轮转为开发材料，不能反复声称是未见测试。
7. **决定并复盘。** 有可解释的收益且没有新增的实质信息错误，才将候选作为新的起点。出现回退就撤回候选或继续修；评审误判、案例含糊和运行问题也要修正并提交。记录哪些问题仍没解决。

## 如何判断收益

信息和任务范围是硬门槛。观点、感受、预测、礼貌和叙述视角也属于原文的一部分，不能只检查数字和名词。删掉一句作者有意表达的话，即使剩余文字更短，也需要作为可能的信息或声音损失检查。

评审先说明这次具体的表达目标，再比较目的适切性、自然中文和模板问题。需要表现力时也检查措辞、节奏与呼应是否起作用，不能只验证已有修辞有没有被删。没有相应需要时，平直、少改或不改可以是更好的选择。允许长句、排比、含蓄和混排，不把最短、最明确或最华丽的输出当作默认赢家。

使用同一原文配不同要求的成对案例，观察重点、力度或解释程度能否随需要变化；也保留同一段内不同作用并存的案例。按组划分开发集和保留集，防止同一原文的另一种要求提前泄漏。评审器记录具体模板问题，不生成 AI 身份判断或检测概率。

改变评判目标时，先用固定的校准对检查评审器：目标改变时偏好应能合理变化，完全相同的输出应允许平局，明显模板外壳应能被定位。校准失败先检查评审方法。新旧评审标准的分数和偏好不能混合计算。

模型评审也会错。需要把它指出的片段回指原文；关系不清或两种表述各有取舍时标为不确定，不勉强计胜负。模型写作与模型评审即使在独立会话中，也可能共享偏好。作者或独立中文编辑的盲评仍是更强的外部证据。

## 本地运行与记录

[`run_evals.py`](../scripts/run_evals.py) 是文本前测工具。它逐例使用 `codex exec --ephemeral`，在临时目录中运行，跳过用户配置、项目文档与宿主 skill 发现，并关闭记忆、插件、连接器和相关工具。模型仍有 Codex 的基础指令；宿主 skill 发现的关闭依赖当前 CLI 的开发中功能，这一限制写入每次 manifest。

运行只复用本机已登录的 ChatGPT 认证，不复制凭据，不把密钥存入仓库，也不启用 API key 计费。首次用于一台机器时先运行 `codex login status` 确认登录方式。脚本只提供评测能力，不安装服务，也不会自动发布或推送。

示例：

```bash
python3 scripts/run_evals.py \
  --skill-ref <完整提交SHA> \
  --suite evals/cases.json \
  --exclude zh-11-file-protection \
  --model <待评测模型> --effort <推理档位> \
  --jobs 2 --timeout 180 \
  --output evals/runs/<本次运行名>
```

文件编辑案例 `zh-11-file-protection` 需要另外在隔离目录做真实文件编辑，不能用文本输出替代后记作通过。文本输入中的注入样例可以运行，引用里的命令不会获得执行授权。

每次输出目录包含 manifest 和逐例 JSON：固定的 skill 提交与内容哈希、案例文件哈希、CLI 版本、模型设置、原始输出、用量、耗时、完成状态及异常。输出目录必须是新的，避免覆盖旧证据。`ok` 只表示执行完整且没有意外工具调用，不表示文章质量通过。超时不自动重试；显式重跑要使用新目录，并在评审记录解释。

容量不足等执行失败可以用相同的输入、模型和设置补跑，调用数仍计入本轮预算。使用 [`complete_eval_run.py`](../scripts/complete_eval_run.py) 将原批次与补跑结果整理到新目录；它核对设置与提示哈希，只接受替换执行失败的项目，不能重抽已经返回的低质量改稿。原始失败批次保持不动，整理目录明确标记为派生视图，不能再计成一次模型运行。服务持续不可用时保留未完成状态，后续再继续，不换模型凑齐比较。

匿名比较时，另存标签映射，给评审会话的材料只含原文、要求、可选样文、验收要点与两份匿名输出。若互换顺序后评判发生实质变化，保留冲突并回到原文复核，说明复核者是谁，不冒充外部人工评审。

官方运行说明：[Codex non-interactive mode](https://developers.openai.com/codex/noninteractive)。当前实现还应以本地 `codex exec --help` 和 `codex features list` 为准。

## 收敛与提交

当前以已验证的 Codex 运行方式开展迭代。每轮先声明采用的依据、开发集、保留集及比较设置。一个问题最多连续尝试两个候选；如果仍没有可复现的收益，保留较好的已验证起点，记录未解决的问题，换一类证据再继续。用户明确修订的目标应先落实，实验无收益时撤回实验部分，不能悄悄退回用户已经否定的固定风格或分类方式。

连续两轮找不到稳定收益时做阶段总结，不靠换词或增加规则制造进度。达到这个停止条件只表示当前材料下暂时收敛，不表示已经证明是“最好的中文 skill”。

正文维持单文件、约当前体量；现有 250 行和 24 KB 是上限，不是扩写目标。改动维护代码时运行仓库校验和单元测试；行为效果只根据实际生成与审阅记录报告。Git commit 可以频繁，发布版本、标签和远端推送按相应授权另行处理。

## 定期继续

当前任务已建立每 4 小时返回一次的 heartbeat，名称为 Humanizer-zh 持续精进，自动化 ID 为 `humanizer-zh`。它会读本任务最新决定和本页，进行资料核对、案例、修改与本地 commit，只有实质成果、失败、阶段完成或需要用户判断时通知。一次最多处理一个候选、16 次编辑或评审模型调用，较大的验证拆到后续运行。

这是本地执行，需要电脑开机、应用运行和项目可访问；运行条件见[官方说明](https://developers.openai.com/codex/app/automations)。如果工作树中有来源不明的改动或另一个活跃修改过程，先保护已有工作，不并行覆盖或提交。定期继续不意味着自动推送、发布，也不要求每次都修改 skill。
