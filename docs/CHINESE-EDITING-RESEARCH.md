# Humanizer-zh 的中文编辑方向

Humanizer-zh 最值得加强的是中文本身的组织方式：一句怎样接住上一句，哪些主语可以省略，动作怎样展开，哪些小词承载了立场，以及中文句子怎样容纳英文术语。现有的去套话、保事实和保语气规则已经提供了基础；下一版可以把这些能力写得更具体，并合并重复提醒，为中文编辑腾出篇幅。

建议继续采用单文件入口。正文保持与现版相近的体量，允许适度增加，但每条新增内容都应说明一个现有规则没有解决的编辑问题。研究依据、来源版本和更多例子留在维护文档中，日常润色只需要根目录的 `SKILL.md`。

本文兼顾技术、产品和说明类文章，以及观点、评论、个人随笔；覆盖简体、繁体和中英混排。以下记录 2026-09-11 的资料核对与建议，区分资料所支持的观察、编辑建议及说明性例子。2026-09-12 已据此写成[本地审阅草稿](../SKILL.md)，取舍见[适配记录](UPSTREAM.md#2026-09-12-中文审阅草稿)；尚未构成经过模型行为验证的发布版本。

## 现有版本的基础与空缺

调研开始时，根目录 skill 共 125 行、4,462 个字符、11,578 字节，含元数据、Markdown 和链接。主体按英文上游的 25 项模式展开，末尾另有四条中文提醒。中文适配已经存在，例如保留正常中文引号、破折号和省略主语，区分真正的术语与工作黑话，并沿用作者的地区用语。[^1][^2][^3]

不足主要在重心：正文较多解释哪些表达容易显得空泛，对怎样形成自然中文的正面说明比较集中、简略。比如“理顺主干”方向正确，却没有充分展示怎样把前置定语展开；“保留语气”也还可以落实到“才、就、还”等容易在润色中丢失的小词。

| 现有能力 | 已经有用的部分 | 值得补强的部分 |
| --- | --- | --- |
| 清理空话 | 空对比、拔高、宣传腔、重复收尾都有具体边界 | 合并相近提醒，让段落推进得到更多篇幅 |
| 信息保真 | 数字、归属、条件、完成状态保护充分 | 把汉语虚词、语序和指代造成的细微差异写成例子 |
| 中文句式 | 已提到省略主语、定语堆叠和名词化 | 展示省略与补明、拆开与保留两种方向 |
| 作者语气 | 已允许不改、参考样文、保留自然重复 | 说明有意味的节奏和细节不只承担事实传递 |
| 中英混排 | 已保护连字符、名称和精确字符 | 加入术语选择、中文句子组织、首次解释和混排标点 |

开头“编号沿用 Blader Humanizer v3.0.0”的介绍属于维护信息，可以从正文删除。“它们是编辑线索，不是禁词表”原意是提醒不要见词就删，但“编辑线索”不够直接，而且各条已经交代保留情形。这里整段删除即可，不必再补一个解释段。

末尾“来源”介绍也可以移出日常使用的入口。仓库已有上游记录和第三方许可文件，继续由这些文件承担追溯与致谢。待改稿里的引文、事实来源和观点归属仍属于需要保留的内容。

## 对“好的中文”的工作定义

对这个 skill，好的中文可以落实为四个可观察的结果：读者容易跟上意思；动作、关系和限定表达准确；句子的轻重停顿符合内容；文章仍保留作者原有的说话方式。技术文档、私人邮件与个人随笔可以用不同的语气达到这些结果。

老舍在谈文学语言时，同时强调普通语言、上下句联系和个人风格；鲁迅的写作答问强调回读与删去可有可无的内容。这些经验支持认真处理语言，但两篇文章都出自文学创作语境，不能直接推导出所有文章都要短句化或缩成摘要。[^4][^5]

可以把“中文更自由”的直觉落实到具体地方：上下文明确时，主语和代词有省略空间；多个分句能够沿着同一件事展开；停顿、语序和小词可以表达细致的关系。与此同时，零形指代也可能产生歧义，语法理论对“零句”等概念的解释存在争论。因此，适合 skill 的是这些可操作的现象，不必采用“中文凭意会、英文靠逻辑”一类概括。[^6][^7]

以下八个方向按编辑价值组织。它们是本项目的建议，不表示各来源共同制定了同一套标准。每个方向都附有原创的修改例子和保留例子；改后只使用原句已给出的信息。

## 一、让句子沿着同一件事往下说

很多文章每句都通顺，连起来却费力：刚提到一个问题，就切到另一个对象；每段先抛一个大判断，再换一组抽象名词。编辑时可以先看上一句让读者关心什么，下一句是否接着交代它。已经出现的对象或问题常常可以成为后一句的起点，不必每句都重新搭一个开头。

这是从篇章连贯和读者需求出发的编辑建议。老舍关于上下句联系的论述，以及 Ant Design 对读者关注点的强调，都能提供启发；后者针对界面文案，因此不能把产品提示的简短结构直接推广到长篇随笔。[^4][^17]

**修改例子**

> 原文：这份教程介绍了安装方法。配置方法也在这份教程的介绍范围内。故障排查是这份教程没有覆盖的内容。
>
> 改后：这份教程介绍了安装和配置方法，没有覆盖故障排查。

调整的是承接和重复的句子外壳，三项内容及其覆盖状态都留下了。长文中也应逐段检查这种关系，而不是把所有内容压成一段。

**保留例子**

> 我还记得那天的雨。至于他后来去了哪里，我一直没有问。

话题的跳转在这里构成作者的叙述选择。原文没有解释两者的因果，编辑也不应补出一个原因来强行衔接。

**进入 skill 的方式**：放入“先改结构”，增加一两句正面目标即可。保留必要的背景、转场和回扣，去掉重复说明同一件事的部分。

## 二、省略要自然，指代要清楚

连续出现的“我们、它、这个工具、你的”容易让中文像逐句翻译。上下文明确时可以省略；对象发生切换、责任需要区分时，则应把对象说清楚。Microsoft 简体中文本地化指南明确允许在不影响意思时省略代词和领属表达；零形指代研究也提醒，省略并不保证所指唯一。[^10][^6]

**修改例子**

> 原文：我昨天试了一个离线笔记工具。我在整理采访录音时用到了这个离线笔记工具。我最喜欢的是这个离线笔记工具的检索功能。
>
> 改后：我昨天试了一个离线笔记工具，用它整理采访录音，最喜欢它的检索功能。

这里仍然是同一个人、同一个工具，不需要反复把两者重新介绍一遍。

**保留例子**

> 编辑把疑问发给作者，作者确认后再发给校对。

第二个“作者”标明了接下来由谁确认、谁转交，不能只为减少重复就删掉。遇到“甲告诉乙，他明天回复”这种原文本身不明确的句子，也不能替作者选一个“他”。

**进入 skill 的方式**：扩展现有“隐去动作和主体”。让这一条同时处理多余的主语与不清楚的指代，不再只朝“补主体”的方向走。

## 三、把动作展开，缩短名词前面的负担

中文中的问题往往不在句子总共有多少字，而在读者是否要先记住一长串修饰，才能知道它们在说什么。可以把过长的定语展开成分句，把已经明确的动作直接写出来。Microsoft 的指南提醒关系从句直译后的修饰堆叠；中文技术文档规范也把代词指向和多重修饰列为编辑问题。[^10][^14]

**修改例子**

> 原文：我们正在测试一个由编辑在浏览器里标记需要复核的句子并由作者逐条确认的流程。
>
> 改后：我们正在测试一个流程：编辑在浏览器里标记需要复核的句子，作者逐条确认。

这比只删几个“的”更有效。先交代“流程”，再按动作展开，原有的执行者、工具、对象和测试状态都不变。

**另一个局部例子**

> 原文：我们完成了对配置文件的修改，并进行了服务的重启。
>
> 改后：我们修改了配置文件，并重启了服务。

**保留例子**

> 请归档已经签字的纸质合同。

“已经签字”和“纸质”都限定了要归档的对象，不能为了简短改成“请归档合同”。“正在进行压力测试”里的“进行”也没有必要见到就删。

**进入 skill 的方式**：合并原来的“隐去动作和主体”“简单动词绕着说”及末尾相关提醒。优先教怎样改句子，避免扩成一份“进行、实现、的”替换表。

## 四、留住小词里的时间、条件和态度

“只有……才”表达条件，“才”和“就”在某些用法中表达与预期的关系。相关研究可以支持把这些差别纳入信息保护；不同语法分析对具体机制存在分歧，skill 不需要选择某一种理论。[^8][^9]

对润色而言，实用做法是同时看这些小词修饰谁，以及整句话因此表达了什么。“还没完成”中的“还”、“看过但没看完”中的“过”，也不能只按字数决定去留。这里需要保护的是上下文中的意思，不是规定任何小词必须原字保留。

**修改例子**

> 原文：我用了三天的时间才把这篇文章改好，但对于标题，我目前还没有想好。
>
> 改后：我花了三天才改好这篇文章，但标题还没想好。

**保留例子**

> 只有收到确认邮件，申请才算完成。

不能改成“收到确认邮件后，可以完成申请”，后者把判定条件写成了后续操作。“三天才改好”和“三天就改好”也不能互换，二者对这段用时的态度不同。

另一个容易忽略的边界是限定范围：“只通知了负责人”与“通知了唯一的负责人”说的不是同一件事。移动“只、都、仅、也”等词时，需要回读它们具体管到哪里。

**进入 skill 的方式**：把这一点加入“保住信息”，配一组短例子。它与一般的“不确定性保护”相关，但能具体补上中文润色容易遗漏的部分。

## 五、按意思安排停顿，保留有作用的重复

句子的节奏可以来自事情发生的次序、观点的转折、读者需要的停顿和作者的语气。连续短句不一定更自然，长句也不必一律拆开。GB/T 15834—2011 把停顿、语气以及成分的性质和作用纳入标点的说明，适合用来支持按关系选标点，而不是按字数切句。[^11]

现有“金句收尾”“凑三项”等检查仍然有用。但删除重复之后，还要看作者的犹豫、强调或回扣是否被一起削掉。说人话的正面风格文档也讨论了承担转场和节奏的重复；可以吸收这个方向，省去它的档位和场景代码。[^2]

**修改例子**

> 原文：我打开文件。读了两页。发现版本不对。于是关掉文件。重新找。
>
> 改后：我打开文件，读了两页，发现版本不对。于是关掉文件，重新找。

动作次序保持原样，发现版本不对之后另起一句。没有为了显得更有情绪而补入“才发现”“竟然”等措辞。

**保留例子**

> 想删掉，又舍不得。放了一夜，还是舍不得。

两个“舍不得”承载了时间经过后的情绪延续。把它压成“我犹豫了一夜”会改掉表达的重心，也会把“放了一夜”解释成持续犹豫。

**进入 skill 的方式**：在“节奏”类加入一个保留例子。逗号、分号、句号和破折号按关系使用，不设置句长配额，也不要求人为制造不规则。

## 六、用词贴合对象，保留中文表达的分寸

可以关注词语是否符合文体，动词是否准确，以及修饰语的轻重是否合适。自然中文不要求把所有词压成最短形式，也不要求用四字词或成语提升文采。这个方向主要是编辑建议；老舍关于普通语言与个人风格的讨论提供原则性参照，不构成一份词语规范。[^4]

**修改例子**

> 原文：对于这个结尾，我的感受是有点舍不得把它删除。
>
> 改后：这个结尾，我有点舍不得删。

这组例子收起了“我的感受是”这层转述，用“删”贴近原有语气，同时保留“有点”的分寸。正式的操作说明使用“删除”也很自然，不需要全篇替换。

**保留例子**

> 那几页写得松松散散，我反而喜欢。

“松松散散”和“反而”都在表达作者的审美。改成“结构有待优化，但具有一定可读性”，虽然显得正式，却已经换了评价和声音。

“走走停停”“恰到好处”也可能很贴切。四字表达、叠词、成语和自然比喻都可以保留，重点看它们是否用得准确、是否符合上下文。

**进入 skill 的方式**：与“留住作者”合并，不另设大量常见词的检查项。除非真实案例持续显示某类搭配会被改坏，否则不扩成语文纠错手册。

## 七、中英混排先解决表达，再处理空格

中英混排至少有三个编辑层面：这个词是否需要保留英文，英文词在中文句子里是否自然，字符和排版是否保持准确。Kubernetes 的中文本地化指南明确区分 API 资源名称与普通词义；这是保留可识别、可检索名称的具体实例。[^16]

**修改例子**

> 原文：这个 API 的使用可以让你进行用户列表的获取。
>
> 改后：用这个 API 可以获取用户列表。

真正改善阅读的是中文句子变直接了，`API` 是否出现并不是问题。

**面向普通读者时的例子**

> 原文：我想先做一次 review，检查一下这段说明。
>
> 改后：我想先检查一下这段说明。

这里原文已说明 `review` 的具体含义，合并没有增加信息。若 `review` 是正式流程名，或是作者和读者一直使用的说法，就不必改成中文。

**保留例子**

> 把 `max_retries` 设为 `0`，保留 `real-time` 这个标签。

这里的大小写、下划线、数值和连字符都是精确字符。名称的内部写法不因中文排版而改动；品牌也不能统一改成首字母大写。

对于首次出现的陌生术语，可以在原文已有解释、已有术语表或允许补充说明的情况下提供简短解释。不要默认给每一个英文缩写补全称，也不要擅自给领域术语选译名。同一对象的中英文叫法应保持一致，不能为了词汇丰富反复轮换。

**进入 skill 的方式**：新增一个短的中英混排段落，并把原第 10 项连字符提醒并入这里。正文最多保留少量原则和一组精确字符例子。

## 八、格式跟随文体和载体

标点和空格值得处理，但不能让润色变成全文件格式清洗。以中文组织的句子一般采用中文标点；完整英文引文、代码和名称内部的字符另行保护。教育部公开的混排标点材料区分了英文单词、词组与完整句子，但其标题明确注明“草案”，只宜作为补充参考。[^12]

W3C《中文排版需求》讨论的是排版呈现，包括中西文之间的间距和不同地区的差别。该文档当前是 Group Note Draft，不能把它说成已经正式认可的统一规范，更不能从视觉间距直接推导出所有文件都必须插入同一种空格字符。[^13]

社区规范也有不同选择：阮一峰的规范允许数字与中文之间的空格采用不同但一致的风格，sparanoid 的指南则规定了更明确的加空格方式。因此，在既有文章中，优先遵循作者、刊物或项目已经使用的格式；新稿没有约定时，再选一套一致的默认值。[^14][^15]

**修改例子**

> 原文：本文介绍 API 的两种用法, 并给出示例。
>
> 改后：本文介绍 API 的两种用法，并给出示例。

**保留例子**

> 错误信息是 `Expected ',' before '}'`。

代码样式中的逗号和引号必须原样保留。修正中文正文的标点，不能顺手改掉英文错误信息。

**进入 skill 的方式**：沿用原有格式和文件保护规则，补充中英交接处的判断。全套标点规范、单位换算、空格替换和简繁转换都不应成为默认改稿动作。

## 资料中的分歧与取舍

不同来源服务的任务不同，采纳时需要连同适用范围一起看。以下取舍尤其影响这个 skill 是否会越写越重。

| 资料或做法 | 值得吸收 | 不直接采用的部分 |
| --- | --- | --- |
| Blader Humanizer | 识别空铺垫、重复意义、助手残留，回读全文 | 不再让上游编号决定中文内容的层级和篇幅；编号对照留给维护者[^1] |
| 说人话正面风格文档 | 语体区别、普通句子、必要重复、信息保真 | 不引入档位、场景代码和额外必读文件；需要新事实的演示不能直接变成润色样例[^2] |
| 早期 Humanizer-zh | 中文入口和直观案例 | 不采用固定自评分，也不靠机械改变并列项数量判断自然度[^3] |
| 作家的写作经验 | 留心表达、回读、连贯和个人声音 | 短句偏好属于具体写作经验，不转换为所有文章的长度限制[^4][^5] |
| Microsoft 简体中文指南 | 处理多余代词、领属语和冗长定语 | 品牌偏好的亲切口吻、“你／您”选择等不成为通用中文风格[^10] |
| 中文技术文档规范 | 清楚的指代、简化修饰、术语一致 | 固定句长上限、全面正式化、每个英文词首次必注等不适用于所有文章[^14] |
| Ant Design 文案规范 | 关注读者、表述一致、重点清楚 | 界面提示的省略程度、正面表达和大小写规则不照搬到一般文章；该页引用的 1995 年标点资料也不能作为新版标准依据[^17][^11] |
| 自动可读性与作文流畅性评测 | 区分不同质量维度，重视可复现材料 | 教材难度和学生作文纠错任务不能直接证明成年人的文章更有个人风格[^18][^19] |

尤其应放弃三种扩展方式：持续增加“AI 高频词”；给自然度设一个看似客观的总分；把每条写作经验配成一套必须执行的判断流程。它们会增加阅读负担，却未必改善编辑结果。

“先判断再修改”的意思仍然需要体现在实际编辑中，但不必在每个层级都强调一次。规则本身写清楚什么时候改、什么时候留，通常比一再解释“这不是禁令”更容易理解。

## 建议的下一版结构与篇幅

保留现有从大处入手的顺序：先读懂用途、保住信息，再看铺垫、节奏、普通信息的表达、格式和正文外壳。中文建议可以成为其中有分量的一节，不必让读者先学习语言学术语。

| 部分 | 建议内容 | 篇幅安排 |
| --- | --- | --- |
| 开头与怎样改 | 保事实、保声音、先结构后句子、回读和停止条件 | 大体沿用，合并重复保护说明 |
| 常见问题 | 保留铺垫、节奏、信息、格式、助手残留等大类 | 将 25 个独立项目收束为约 12–16 个编辑问题 |
| 中文怎么写顺 | 承接与省略、展开动作、限定小词、停顿和个人语气 | 从四条摘要扩成约六条有例子的建议 |
| 中英混排 | 名称与普通词、中文句式、首次解释、字符和标点 | 约两条，吸收现有连字符提醒 |
| 交付 | 一版正文、按需说明、只标问题、文件保护 | 保持简短，不在末尾加入来源介绍 |

这些数量是起草预算，不是行为指标。建议下一版总字符约 4,500–6,000，按当前排版大约 140–200 行；实际以例子和规则是否有用为准。仓库现有的 250 行、24 KB 校验是上限，不应当作扩写目标。也不应为了看起来行数少，把更多要求塞进一条很长的句子。

优先合并的位置比较明确：原第 11、18 项和末尾动作提醒有重合；第 2、13、15 项都部分处理没有新增内容的收尾；第 4、24 项都涉及提示或重述；第 10 项可并入中英混排。合并时仍要保留它们各自有用的边界，例如真实因果与空泛意义不同，步骤引导与空预告也不同。

重新组织规则时，还需要调整校验脚本中强制保留 1–25 编号的要求，并让上游对照表按规则名称或主题映射。上游固定提交只在实际审阅对应变化后更新；中文自身的重新编排不构成推进上游基线的理由。

## 怎样验证这些建议是否有帮助

仓库已有 16 个合成回归案例，覆盖事实、归属、语气、格式、长文范围和只标问题等边界。这些仍应保留。新增中文规则后，需要补上让新规则有机会改进、也有机会误改的成对案例。

| 新的案例方向 | 应该改善的输入 | 必须保留的对应情形 |
| --- | --- | --- |
| 主语与指代 | 同一主体、同一对象被重复介绍 | 多个主体交接责任，或原文指代不明确 |
| 定语展开 | 一长串修饰把中心词压到最后 | 限定了对象范围、不能删减的修饰 |
| 小词与范围 | 句子绕口但含“才、还、只” | 必要条件、完成状态和作者对用时的态度 |
| 连贯 | 多句反复介绍同一对象 | 有意转场、悬念和时间跳跃 |
| 节奏 | 一串无必要的碎句 | 承担犹豫、强调、回扣的短句和重复 |
| 中英混排 | 英文名词外套了冗长中文结构 | API 名、变量、品牌和自然的行业表达 |
| 格式 | 中文正文混入误用的英文标点 | 引文、错误信息和代码中的精确字符 |
| 文体 | 同一模板铺满不同文章 | 个人随笔、正式邮件、技术文档各自的声音 |

比较时，用同一模型和相同设置运行现版与候选版，保持原文、要求和样文一致。把两份结果的顺序随机化，审阅者先看信息有没有漂移，再比较中文是否更顺、是否保留作者。保留原始输出、模型标识和失败理由；不能只展示挑选出的成功例子。

可以分批验证：先做与新规则相关的成对样例，再做现有全量回归。由于模型输出有波动，对接近或矛盾的结果重复运行，比为每个案例设一个精确的自然度分数更有意义。有条件时由作者本人或独立中文编辑参加盲评；若只有改写者自查，就明确记录这一限制。

通过门槛应优先看事实与范围：任何新编事实、主体错配、条件漂移、精确字符损坏都要单列，不能用流畅性加分抵消。随后再看改善是否在不同文体都出现，以及本来已经自然的文本是否被过度修改。真实文章还需覆盖跨段落承接，不能仅凭短句测试宣布适合长文。

中文自动可读性研究主要衡量阅读难度，CEFE 任务主要面向中小学生作文中的流畅性与语法错误。它们帮助区分评测目标，但这里需要另行验证作者声音、信息保真和中英混排，不能直接借用那些研究的结果宣称本 skill 已有效。[^18][^19]

## 当前可确认的结论

现版的保真和文体边界值得保留。新增内容应集中在中文句子和篇章的具体编辑动作，并用原文与改后的对照证明它们没有篡改意思。中英混排值得有自己的短段落，格式处理则应服从正文和项目惯例。

本报告完成的是资料核对、规则取舍和原创例子的静态自查；没有进行独立模型行为评测。现有 16 个案例用于核对覆盖面，尚未按候选规则生成并审阅一轮新输出。因此，这里提出的是可验证的编辑方向，不是“已经做到最好”的效果结论。
